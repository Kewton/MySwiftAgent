## 6. 改善提案

### 必須改善項目（Must Fix）

**なし** - 設計は要件を満たしており、重大な問題は検出されませんでした。

### 推奨改善項目（Should Fix）

#### SF-1: エラー状態の詳細化

**現状**: エラーハンドリングで `console.error` のみ

**提案**: ユーザー向けエラーメッセージの状態変数を追加

```typescript
// 追加提案
let errorMessage: string | null = null;

// エラーハンドラー内
catch (error) {
  errorMessage = 'フィードバックの送信に失敗しました。再度お試しください。';
  console.error('Failed to submit feedback:', error);
}
```

**理由**: ユーザーがエラーを認識し、対処できるようにする

#### SF-2: フィードバックスキップ機能

**現状**: 候補確定後、フィードバックモーダルが必ず表示される

**提案**: フィードバックをスキップするオプションを追加

```svelte
<!-- FeedbackModal内に追加 -->
<button on:click={handleSkip}>スキップ</button>
```

**理由**: 全ユーザーがフィードバックを送信するとは限らない。UXの柔軟性向上

### 検討事項（Consider）

#### C-1: 候補選択状態の永続化（将来検討）

**背景**: 現在はローカル状態で、画面リロードで消失

**検討**: 長時間のチャットセッションでの候補選択状態をlocalStorageに保存

**判断**: 現時点では不要（YAGNI適用）。ユーザーからの要望があれば実装

#### C-2: フィードバック送信のオプティミスティック更新

**背景**: 現在は送信完了まで待機

**検討**: 送信前にUIを更新し、失敗時にロールバック

**判断**: 現時点では不要。フィードバック送信は頻繁でなく、500ms以内で完了予定

#### C-3: 候補のドラッグ&ドロップ並べ替え

**背景**: 複数候補の優先度を視覚的に操作

**検討**: 将来の機能拡張として検討

**判断**: 現時点では不要（YAGNI適用）

## 7. ベストプラクティスとの比較

### 業界標準との差異

| 項目 | 業界標準 | 本設計 | 差異評価 |
|------|---------|--------|---------|
| **状態管理** | Redux/Zustand/Jotai | Svelte Store（ローカル状態） | ✅ 適切（Svelteエコシステムに最適化） |
| **コンポーネント設計** | Atomic Design | 機能単位のコンポーネント | ✅ 適切（プロジェクト規模に合致） |
| **エラーハンドリング** | Error Boundary | try-catch + 状態変数 | ✅ 適切（Svelteの標準パターン） |
| **API呼び出し** | React Query/SWR | 直接fetch | ⚠️ 検討余地あり（キャッシュ機能なし） |

### 代替アーキテクチャ案

#### 代替案1: MLOps Chat画面を実際のLLMチャットと統合（案B）

**メリット**:
- MLOps機能の集約
- Create Job画面の複雑化を回避

**デメリット**:
- 既存Create Jobワークフローの変更が必要
- ユーザー導線が分断される

**評価**: 不採用が妥当（既存ワークフロー維持が優先）

#### 代替案2: 候補選択を別ページに分離

**メリット**:
- 機能の明確な分離
- テスト容易性向上

**デメリット**:
- 画面遷移によるUX低下
- 会話のコンテキスト維持が複雑化

**評価**: 不採用が妥当（シームレスなUXが優先）
