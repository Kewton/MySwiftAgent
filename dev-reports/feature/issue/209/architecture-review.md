#### MF-1: conftest.py共通化戦略の明確化

**問題**: 設計方針書でconftest.pyの重複が懸念されているが、具体的な共通化戦略が不明確

**推奨対策**:
```python
# tests/conftest_common.py を作成し共通フィクスチャを集約
# tests/integration/python/conftest.py から参照

# tests/conftest_common.py
import pytest
from typing import Generator

@pytest.fixture(scope="session")
def docker_compose_command():
    """共通: Docker Composeコマンド生成"""
    return "docker compose"

# tests/integration/python/conftest.py
from tests.conftest_common import docker_compose_command  # 共通利用
```

### 8.1 評価サマリ

| カテゴリ | スコア |
|---------|--------|
| 設計原則遵守 | ⭐⭐⭐⭐☆ (4.5/5) |

| セキュリティ | ⭐⭐⭐⭐⭐ (5.0/5) |
| 既存システム整合性 | ⭐⭐⭐⭐⭐ (5.0/5) |
| リスク対応 | ⭐⭐⭐⭐☆ (4.0/5) |
| **総合** | **⭐⭐⭐⭐☆ (4.6/5)** |

### 8.2 強み

1. **段階的移行**: 既存システムへの影響を最小化しつつ、段階的に新構造へ移行可能
2. **レイヤー分離**: 「1 Issue = 1 Layer」ルールにより、変更の影響範囲が明確
3. **セキュリティ**: APIキーを含む受入テストのCI除外により、シークレット漏洩リスクを根本的に排除
4. **既存資産活用**: pytest/Vitest/Makefileなど既存ツールを最大限活用

### 8.3 弱み

1. **ドキュメント依存**: テスト実行場所の判断がドキュメント依存度が高い
2. **conftest重複**: 共通フィクスチャの重複管理に注意が必要
3. **Playwright学習コスト**: TypeScript E2Eテストに新規ツール導入

### 8.4 総評

本設計は、MySwiftAgentのマイクロサービスアーキテクチャに適した**実用的かつ堅実なテスト構造改善案**です。

特に以下の点で優れています：
- 既存CI/CDへの影響を最小化しながら受入テストを分離
- レイヤー別のテスト責任を明確化し、開発プロセスの品質向上に寄与
- セキュリティリスク（APIキー漏洩）への根本的対策

一方、以下の改善により更に堅牢な設計になります：
- conftest.py共通化戦略の明確化
- テスト実行場所の視覚的明示化
- PRテンプレートの早期導入
