## 1. reasoning フィールド省略の根本原因

### 1.1 問題の概要

self_repair ループでLLMが `reasoning` フィールドを省略し、Pydantic ValidationError が発生する。

### 1.2 根本原因の分析

#### 原因1: 極めて長いベースプロンプト（約550行）

**ファイル**: `workflow_generation.py`

```
Lines 1-546:
- システムプロンプト: 約60行
- ユーザープロンプト: 約490行
  - Task Metadata: ~20行
  - Available GraphAI Agents: 動的（約20-30行）
  - Available ExpertAgent APIs: 動的（約100-200行）
  - YAML Generation Rules: ~300行（詳細なルール、例、ベストプラクティス）
  - Response Format: 最後の15行
```

**問題点**:
- Response Format 要件（`reasoning` 必須）がプロンプトの **最後** に記載
- LLMは長いプロンプトの末尾の指示を見落とす傾向がある

#### 原因2: フィードバックプロンプトがさらに長くなる

**ファイル**: `workflow_generation.py:551-594`

```python
def create_workflow_generation_prompt_with_feedback(...):
    base_prompt = create_workflow_generation_prompt(...)  # ~550行

    feedback_section = f"""
## Previous Generation Errors
...
## Required Fixes
1. Fix YAML syntax errors if any
2. Correct agent names
3. Fix data flow issues
4. Validate input/output schema
5. Add missing error handling
"""  # +20行
```

**問題点**:
- フィードバックセクションはYAML修正に焦点を当てている
- **`reasoning` フィールドの要件について言及していない**
- LLMは「YAML修正が主目的」と解釈し、`reasoning` を省略

#### 原因3: self_repair ノードのフィードバック内容

**ファイル**: `self_repair.py:65-76`

```python
error_feedback_lines.extend([
    "",
    "Please regenerate the workflow and resolve every issue listed.",
    "Ensure:",
    "- YAML syntax is 100% correct",
    "- All agent names exist in available_agents list",
    "- Data flow (:references) are correct",
    "- HTTP API calls use fetchAgent with correct URL/method/body",
    "- Final output node has isResult: true",
])
```

**問題点**:
- **`reasoning` フィールドについての言及がない**
- LLMは「YAMLの修正が重要」と判断し、出力を最小化

#### 原因4: LLMの出力長制限と優先順位付け

LLMは長いプロンプトに対して出力を最適化する際：
1. **必須の成果物（`yaml_content`）を優先**
2. **説明的なフィールド（`reasoning`）を省略**
3. 特にリトライ時は「修正されたYAML」に集中

### 1.3 失敗フローの詳細

```
[初回生成] - 成功率高い
generator (attempt 1)
  ↓ プロンプト: ~550行
  ↓ LLM出力: { workflow_name, yaml_content, reasoning } ← 全フィールド含む
  ↓ status: yaml_generated

[リトライ時] - 失敗率高い
self_repair
  ↓ error_feedback: YAMLエラーのリスト + 修正指示
  ↓
generator (attempt 2)
  ↓ プロンプト: ~570行 (base + feedback)
  ↓ LLM出力: { workflow_name, yaml_content } ← reasoning 省略！
  ↓ Pydantic ValidationError: reasoning Field required
  ↓ status: failed
```

### 1.4 問題箇所のまとめ

| 問題 | ファイル | 行 | 説明 |
|------|---------|-----|------|
| Response Format が末尾 | `workflow_generation.py` | 531-546 | プロンプト末尾に配置 |
| feedback に reasoning 言及なし | `workflow_generation.py` | 571-594 | YAML修正のみに焦点 |
| self_repair に reasoning 言及なし | `self_repair.py` | 65-76 | YAML要件のみリスト |
| reasoning が必須フィールド | `workflow_generation.py` | 74-76 | Optional でない |

## 2. recommended_apis 不足の根本原因

### 2.1 問題の概要

タスクブレイクダウンで `recommended_apis` に具体的なエンドポイントが指定されず、ワークフロー生成時に適切なAPIが選択されない。

### 2.2 根本原因の分析

#### 原因1: 評価基準が緩すぎる（Issue #305 "緩和版 v2"）

**ファイル**: `evaluation.py:615-738`

```python
# Issue #305: API keywords that indicate specific API intent
api_keywords = [
    "jsonoutput", "gmail", "メール送信", "メール検索", "メール",
    "text_to_speech", "tts", "音声合成", "音声", "drive", ...
]
```

**評価ロジック** (lines 696-703):
```
1. まず recommended_apis に有効なエンドポイント（/v1/...）が含まれているか → OK
2. API種別キーワードが含まれているか → OK
3. タスク名（name）にAPI種別キーワードが含まれているか → OK  ← ★ここが問題
4. 説明（description）にAPI種別キーワードが含まれているか → OK  ← ★ここが問題
5. すべて該当しない場合のみ → 問題あり
```

**問題点**:
- タスク名に「メール送信」と書いてあれば、`recommended_apis: fetchAgent` でも **問題なし** と判定
- **実際のエンドポイント (`/v1/utility/gmail/send`) が指定されているかは検証しない**

#### 原因2: レガシー形式の自動変換

**ファイル**: `task_breakdown.py:218-267`

```python
@field_validator("recommended_apis", mode="before")
def convert_string_apis_to_objects(cls, v):
    """Convert legacy string format to RecommendedAPI objects."""
    for item in v:
        if isinstance(item, str):
            # "fetchAgent" → RecommendedAPI(api_name="fetchAgent", endpoint="", ...)
            result.append({
                "api_name": item,
                "endpoint": extracted_endpoint,  # 抽出できなければ空文字
                "reason": "LLMが推奨（レガシー形式から自動変換）"
            })
```

**問題点**:
- LLMが `["fetchAgent"]` のような単純な文字列を返しても、自動的にオブジェクトに変換
- エンドポイントが空でも **エラーにならない**
- この後方互換性が「甘い評価」を可能にしている

#### 原因3: task_api_mapping が参照情報のみ

**ファイル**: `expert_agent_capabilities.yaml:689-837`

```yaml
task_api_mapping:
  - task_type: "メール送信"
    keywords: ["メール送信", "通知", "Gmail送信", "メール通知"]
    recommended_api:
      api_name: "Gmail送信"
      endpoint: "/v1/utility/gmail/send"
    reason: "高速Direct API（3-5秒）でメール送信可能"
```

**問題点**:
- この情報はプロンプトに含まれているが、**LLMが採用するかは確率的**
- 評価時に「task_api_mapping に従っているか」の検証がない
- キーワードマッチングによる推奨は行われていない

#### 原因4: タスクブレイクダウンプロンプトが長すぎる

**ファイル**: `task_breakdown.py`

```
システムプロンプト: ~600行
- 5原則の説明: ~100行
- 利用可能なAPI種別: ~50行
- expert_agent_capabilities: 動的（~200行）
- recommended_apis の記述ルール: ~50行
- タスク種別ごとの推奨API: ~20行
- 制約条件: ~20行
- タスク分割の例: ~130行（2つの詳細な例）
- 出力形式: ~30行
```

**問題点**:
- プロンプトが非常に長いため、LLMは全ての指示を正確に従わない
- 特に「recommended_apis は構造化された形式で記述」の要件が守られないことがある

### 2.3 v1.37 での具体的な失敗例

| タスク | タスク名 | recommended_apis | 評価結果 | 問題点 |
|--------|---------|-----------------|----------|--------|
| Task 2 | IR資料のWeb検索実行 | `fetchAgent` | ✅ PASS | 「検索」キーワードで通過 |
| Task 3 | PDF URLの特定と選別 | `fetchAgent` | ✅ PASS | 具体的APIなし |
| Task 4 | IR資料からの重要セクション抽出 | `fetchAgent` | ✅ PASS | 抽出処理の具体的APIなし |
| Task 5 | 財務・事業データの構造化 | `fetchAgent` | ✅ PASS | 構造化処理の具体的APIなし |
| Task 6 | 5年間の変遷分析とレポート生成 | `fetchAgent` | ✅ PASS | 分析処理の具体的APIなし |

**結果**:
- 全タスクが評価を通過
- しかし、ワークフロー生成時に具体的なAPIが分からず、汎用的な `jsonoutput` API を使用
- 複雑なタスクには不十分 → LLM Evaluator で低スコア → self_repair ループ → reasoning 省略 → 失敗

## 3. 2つの問題の相関関係

```
[Task Breakdown]
     ↓
recommended_apis が抽象的（例: fetchAgent のみ）
     ↓
評価: キーワードマッチで PASS
     ↓
[Workflow Generation]
     ↓
具体的なAPIが分からず、汎用的なアプローチを採用
     ↓
[LLM Evaluator]
     ↓
低スコア（API選択が不適切）
     ↓
[self_repair]
     ↓
フィードバック: YAML修正に焦点
     ↓
[generator (retry)]
     ↓
★ reasoning を省略
     ↓
Pydantic ValidationError → FAILED
```

**結論**: 2つの問題は独立しているように見えるが、実際には連鎖的に影響し合っている。

## 6. 結論

### reasoning 省略問題

**根本原因**: リトライ時のフィードバックがYAML修正のみに焦点を当てており、LLMが `reasoning` フィールドを「不要」と判断して省略する。

**主な要因**:
1. Response Format 要件がプロンプト末尾（見落としやすい）
2. feedback セクションに reasoning 要件の言及なし
3. self_repair のエラーフィードバックに reasoning 言及なし
4. `reasoning` が Optional でない

### recommended_apis 不足問題

**根本原因**: 評価基準が「緩和版 v2」として緩すぎ、タスク名や説明にキーワードがあれば具体的なエンドポイントがなくても通過する。

**主な要因**:
1. キーワードマッチのみで具体的 endpoint の検証なし
2. レガシー形式（文字列）の自動変換が甘い評価を許容
3. task_api_mapping が参照情報のみで強制されない
4. タスクブレイクダウンプロンプトが長すぎてLLMが全指示に従わない
