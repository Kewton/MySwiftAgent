# v1.37 ワークフロー失敗問題 調査レポート

**Issue**: #305
**対象**: v1.37 Job Generation
**調査日**: 2025-12-25
**ステータス**: 調査完了（対応未実施）

---

## 1. 問題概要

v1.37 において、7タスク中5タスクでワークフロー生成が失敗した。

| タスク | ステータス |
|--------|----------|
| 1. 検索クエリの生成 | ✅ success |
| 2. IR資料のWeb検索実行 | ❌ failed |
| 3. PDF URLの特定と選別 | ❌ failed |
| 4. IR資料からの重要セクション抽出 | ❌ failed |
| 5. 財務・事業データの構造化 | ❌ failed |
| 6. 5年間の変遷分析とレポート生成 | ❌ failed |
| 7. 分析レポートのメール送信 | ✅ success |

**成功率**: 2/7 (28.6%)

---

## 2. 重要な発見

### すべての失敗タスクに共通する根本原因

**深掘り調査の結果、当初3パターンに分類した失敗は、実際には1つの根本原因に収束することが判明した。**

| 当初の分類 | 実際の原因 |
|-----------|----------|
| パターンA: YAML未生成 (Task 2, 6) | **reasoning フィールド欠落** |
| パターンB: reasoning欠落 (Task 4, 5) | **reasoning フィールド欠落** |
| パターンC: バリデーション失敗 (Task 3) | **テストデータ品質不足 + LLM評価スコア低下** |

---

## 3. 詳細調査結果

### 3.1 パターンA・B の統合：reasoning フィールド欠落

**Langfuse トレース調査結果**:

| タスク | Trace ID | Generator Status | 実際のエラー |
|--------|----------|-----------------|-------------|
| Task 2 | f9f5414028f849df99ed5e988bbe6f7a | failed | `reasoning Field required` |
| Task 4 | d944435d49344042b385d46e3490e864 | failed | `reasoning Field required` |
| Task 5 | 5ccaea7edf6e476ca5aaf191f05bf265 | failed | `reasoning Field required` |
| Task 6 | a41e5fe9e353495cb1565db75e765952 | failed | `reasoning Field required` |

**観察事項**:

1. **初回生成は成功することが多い**
   - Task 4, 5: 最初の generator 呼び出しは `status: yaml_generated`
   - YAML は正常に生成されている

2. **リトライ時に reasoning が欠落**
   - self_repair ループで generator が再度呼び出される
   - 2回目以降の呼び出しで LLM が reasoning を省略
   - Pydantic ValidationError が発生

**エラーメッセージの詳細**:
```
workflow_generation failed: 1 validation error for WorkflowGenerationResponse
reasoning
  Field required [type=missing, input_value={'workflow_name': '...', 'yaml_content': '...'}, input_type=dict]
```

**根本原因**:

`WorkflowGenerationResponse` スキーマ（`workflow_generation.py:65-76`）:
```python
class WorkflowGenerationResponse(BaseModel):
    workflow_name: str = Field(...)
    yaml_content: str = Field(...)
    reasoning: str = Field(...)  # ★ 必須フィールド - LLMが省略するとエラー
```

**なぜ LLM は reasoning を省略するのか**:
- self_repair プロンプトにエラーフィードバックが追加される
- プロンプトが長くなり、LLM が出力を省略する傾向
- 特に複雑なタスク（Web検索、長期分析）で発生しやすい

### 3.2 パターンC：テストデータ品質不足 (Task 3)

**処理フロー**:
```
generator (yaml_generated) → workflow_tester (HTTP 200) → validator (is_valid: true)
→ llm_evaluator (score: 42) → self_repair → generator → ... → max_retries_exceeded
```

**LLM Evaluator スコア内訳**:

| スコア項目 | 値 | 問題点 |
|-----------|-----|--------|
| Overall Score | 42 | 閾値 70 未満 |
| Structural Score | 75 | ✅ OK |
| Requirement Score | 70 | ✅ OK |
| Output Quality Score | 35 | ❌ 低い |
| Error Handling Score | 50 | ⚠️ 中程度 |
| **Test Data Quality Score** | **15** | **❌ 致命的に低い** |

**テストデータの問題点**:

生成されたサンプル入力:
```json
{
  "search_results": [
    {
      "year": 1,                         // ❌ 非現実的（2023などが期待される）
      "document_type": "sample_text",    // ❌ 「有価証券報告書」等が期待される
      "results": [
        {
          "title": "Sample Title",
          "url": "https://example.com/sample",  // ❌ .pdf が期待される
          "snippet": "sample_text"
        }
      ]
    }
  ]
}
```

**sample_input_generator.py の問題**:

```python
# Line 179-180: integer は常に 1 を返す
if schema_type == "integer":
    return 1

# Line 130: パターンマッチしない string は "sample_text" を返す
return "sample_text"
```

**stringTemplateAgent の問題**:
```
Execution failed due to invalid test data format
(stringTemplateAgent converted object to '[object Object]')
```

## 5. 問題点の階層構造

```
根本原因
├── 1. reasoning フィールド必須制約 (Task 2, 4, 5, 6)
│   ├── LLMがself_repairループで reasoning を省略
│   ├── 長いプロンプトで出力が切り詰められる傾向
│   └── Pydantic ValidationError で処理終了
│
└── 2. テストデータ品質不足 (Task 3)
    ├── sample_input_generator が非現実的な値を生成
    │   ├── integer → 常に 1
    │   └── string → 常に "sample_text"
    ├── stringTemplateAgent の JSON シリアライズ問題
    └── LLM Evaluator が低スコアを付与（42/100）
```

## 7. 考えられる対策オプション（参考）

### 7.1 即効性のある対策

| 対策 | 効果 | 変更箇所 |
|------|------|---------|
| `reasoning` を `Optional` に変更 | Task 2, 4, 5, 6 の失敗解消 | `workflow_generation.py:74` |
| `reasoning` にデフォルト値設定 | 同上 | `workflow_generation.py:74` |

### 7.2 テストデータ品質改善

| 対策 | 効果 | 変更箇所 |
|------|------|---------|
| integer にコンテキスト依存値 | year=2024 等を生成 | `sample_input_generator.py:179` |
| string にドメイン知識追加 | document_type に適切な値 | `sample_input_generator.py:130` |
| LLM によるテストデータ生成 | 全体的な品質向上 | 新規ノード追加 |

### 7.3 リトライ時の安定性向上

| 対策 | 効果 | 変更箇所 |
|------|------|---------|
| self_repair プロンプト簡略化 | LLM 出力省略防止 | `workflow_generation.py` |
| リトライ回数増加 | 成功確率向上 | `state.py` |
| 部分成功の保持 | 初回成功時の YAML を保持 | `generator.py` |

## 9. 結論

v1.37 の5タスク失敗は、主に2つの根本原因に起因する：

### 1. reasoning フィールド必須制約（Task 2, 4, 5, 6）

- **現象**: self_repair ループで LLM が `reasoning` を省略
- **結果**: Pydantic ValidationError で処理終了
- **影響**: 4タスク失敗
- **優先度**: 🔴 高

### 2. テストデータ品質不足（Task 3）

- **現象**: sample_input_generator が非現実的な値（year=1, "sample_text"）を生成
- **結果**: LLM Evaluator が低スコア（42/100）を付与、リトライしても改善せず
- **影響**: 1タスク失敗
- **優先度**: 🟡 中

特に **reasoning フィールド問題** は、Issue #305 の `fast_mode=False` 変更により LLM Evaluator が常に実行されるようになり、self_repair ループが頻繁に発生するようになったことで顕在化した。
