## 5. コンポーネント間論理的整合性（Issue #359/360）

### 5.1 型定義の不整合

**❌ 重大な矛盾発見**

| 概念 | 設計方針書の定義 | 既存workflow.types.ts | 整合性 | 対処案 |
|------|-----------------|---------------------|--------|--------|
| WorkflowDefinition | `workflow_name`, `input_schema`, `output_schema`, `steps[], output` | `id`, `name`, `version`, `steps[]`, `variables`, `timeout` | ❌ 不一致 | 統一または変換層が必要 |
| Step構造 | graphAiServer形式（`type: NodeType`） | 汎用形式（`type: string`） | ❌ 不一致 | 型の拡張が必要 |
| ステータス | `success/partial_success/failed` | 同じ（ExecutionStatus） | ✅ 一致 | - |

**対処案**:
```typescript
// 新しい型定義を追加
export interface TaskFlowDefinition extends WorkflowDefinition {
  workflow_name: string;  // nameのエイリアス
  input_schema: IOSchemaType;
  output_schema: IOSchemaType;
  output: Record<string, string>;
}
```

### 5.2 部分成功モデルの整合性

**⚠️ 潜在的な矛盾**

| 処理 | 設計での扱い | 既存実装での扱い | 問題 |
|------|------------|---------------|------|
| ステップ失敗時 | `partial_success`を返す | ExecutionStatusで対応 | ✅ OK |
| 並列実行の部分失敗 | 言及あり | 詳細な実装方針なし | ⚠️ 曖昧 |
| エラー情報の伝播 | `errors[]`で伝達 | StepError[]で対応 | ✅ OK |

**改善提案**: 並列実行時の部分成功判定ロジックを明確化する

### 5.3 エラーコードの重複定義チェック

**⚠️ 潜在的な重複**

| エラーコード | TaskFlowErrorCode | 他の場所での定義 | 対処案 |
|-------------|------------------|----------------|--------|
| VALIDATION_ERROR | ✅ 定義済み | 他モジュールでも使用の可能性 | 共通エラーコード定義の検討 |
| TIMEOUT | ✅ 定義済み | - | - |

### 追加された設計方針

#### DP-5: 型定義の整合性確保（アダプターパターン）
- `TaskFlowDefinition`（graphAiServer互換）と`InternalWorkflowDefinition`（内部形式）の双方向変換
- 既存コードへの影響を最小化しつつ互換性を維持

#### DP-6: code_jsノードのセキュリティ強化
- `isolated-vm`によるメモリ隔離実行
- ホワイトリストによる許可制スクリプト実行
- SHA-256による整合性検証
- システムリソースアクセスの完全制限

#### DP-7: 並列実行制御の具体化
- グローバル制限（50並列）、ワークフロー制限（10並列）、ノードタイプ制限（LLM: 5並列等）
- メトリクス収集による運用監視
- キュー待機タイムアウト（60秒）によるリソース保護

### 総評

設計方針書の改訂により、当初指摘した3つの重大な懸念事項がすべて解消されました。
特に以下の点が高く評価できます：

1. **アダプターパターン**の採用により、既存システムとの互換性を維持しながら内部の一貫性を確保
2. **多層防御**によるcode_jsノードのセキュリティ（隔離実行 + ホワイトリスト + 整合性検証）
3. **3層並列制限**による柔軟かつ安全なリソース管理とメトリクス収集

高品質で保守性の高いTaskFlow実行エンジンの実装が期待できます。
