## 5. リスク評価

| リスク種別 | 内容 | 影響度 | 発生確率 | 対策優先度 |
|-----------|------|-------|---------|-----------|
| **技術的リスク** | Coalesceチェーンの複雑な参照解決によるバグ | 中 | 中 | 🔴 高 |
| **技術的リスク** | isJsonString誤判定（例: '{name}'が文字列なのにJSONと判定） | 低 | 低 | 🟢 低 |
| **運用リスク** | チュートリアル更新漏れ | 低 | 低 | 🟢 低 |
| **セキュリティリスク** | Coalesceチェーンによる無限ループ | 中 | 低 | 🟡 中 |
| **ビジネスリスク** | 既存ワークフローの破壊的変更 | 中 | 極低 | 🟢 低 |

### リスク詳細分析

#### リスク1: Coalesceチェーンの複雑な参照解決

**発生シナリオ**: 複数の参照がすべてundefinedの場合の処理、循環参照

**対策**:
- 単体テストで網羅的にエッジケースをカバー
- 循環参照検出ロジックの追加（オプション）

#### リスク2: isJsonString誤判定

**発生シナリオ**: `"{name}"` のようなJSONライクな文字列

**対策**:
- 実際のJSON.parseで検証（try-catch）
- 誤判定時もフォールバックで動作継続

#### リスク3: Coalesceチェーンによる無限ループ

**発生シナリオ**: `${a ?? b}` と `${b ?? a}` の相互参照

**対策**:
- 参照解決のスタック管理
- 解決中の参照セットを追跡し、循環を検出

## 6. 改善提案

### 必須改善項目（Must Fix）

1. **Coalesceチェーン数の上限設定**
   - 設計方針書で「最大10個」と記載があるが、実装コードへの反映を確認
   - 定数として明示的に定義（例: `MAX_COALESCE_REFERENCES = 10`）

2. **循環参照検出**
   - Coalesceチェーン内での循環参照を検出するロジック追加
   - エラーメッセージで問題の参照パスを明示

### 推奨改善項目（Should Fix）

1. **エラーメッセージの改善**
   ```typescript
   // Before
   throw new Error('Invalid coalesce chain');

   // After
   throw new Error(`Coalesce chain exceeds maximum depth (${MAX_COALESCE_REFERENCES}): ${reference}`);
   ```

2. **isJsonString のロバスト化**
   ```typescript
   private isJsonString(str: string): boolean {
     const trimmed = str.trim();
     // より厳密な判定
     if (!trimmed.startsWith('{') && !trimmed.startsWith('[')) {
       return false;
     }
     try {
       JSON.parse(trimmed);
       return true;
     } catch {
       return false;
     }
   }
   ```
   ただし、パフォーマンスとのトレードオフを考慮。現在の簡易判定でも実用上は問題なし。

3. **テストカバレッジの明示的な目標設定**
   - transform-node.test.ts: 新機能のカバレッジ100%
   - context-manager.test.ts: Coalesceチェーンのエッジケース網羅

### 検討事項（Consider）

1. **Phase 2 の `_conditional` 変数実装時期**
   - 現在のCoalesceチェーンで十分な場合、Phase 2は延期可能
   - ユーザーフィードバックに基づいて判断

2. **型安全性の強化**
   - TypeScript strict modeでのコンパイル確認
   - Coalesceチェーンの戻り値型推論

3. **ドキュメンテーション**
   - 新機能（Coalesceチェーン）のユーザードキュメント作成
   - チュートリアルへの使用例追加

## 7. ベストプラクティスとの比較

### 業界標準との差異

| 観点 | 業界標準 | 本設計 | 評価 |
|-----|---------|-------|------|
| **テンプレートエンジン拡張** | ヘルパー登録 | ヘルパー登録 | ✅ 一致 |
| **Null合体演算子** | `??` オペレータ | `??` 構文 | ✅ 一致（JavaScript標準に準拠） |
| **JSON自動検出** | 明示的指定が一般的 | 自動検出 | ⚠️ 差異あり（利便性優先の判断） |
| **条件分岐結果格納** | 特殊変数（$result等） | Coalesce + Phase2で_conditional | ✅ 適切 |

### 代替アーキテクチャ案

#### 代替案1: Expression Language導入

**説明**: Handlebarsの代わりにJEXL等の式言語を導入

**メリット**:
- より強力な式評価
- @index等の特殊変数を自然にサポート

**デメリット**:
- 既存Handlebarsとの非互換
- 学習コスト増加
- セキュリティ評価の再実施必要

**評価**: 採用しない（破壊的変更、ROI低い）

#### 代替案2: Transform Modeの分離

**説明**: Map/Merge等の各モードを個別のノードタイプとして実装

**メリット**:
- 単一責任原則のさらなる徹底
- 各ノードのテストが独立

**デメリット**:
- ノードタイプの増加
- 既存ワークフローの修正必要

**評価**: 将来的に検討（現時点では過剰設計）
