## 1. 設計原則の遵守確認

### SOLID原則チェック

| 原則 | 評価 | 詳細 |
|------|------|------|
| **S**ingle Responsibility | ✅ 適切 | `RunRepository`はデータアクセスのみ、`createRunPollingStore`はポーリング状態管理のみを担当 |
| **O**pen/Closed | ✅ 適切 | ポーリングストアはファクトリ関数で拡張可能、WebSocket化への移行余地あり |
| **L**iskov Substitution | ✅ 適切 | 既存の`ApiClient`基底クラスパターンを正しく踏襲 |
| **I**nterface Segregation | ✅ 適切 | `Run`, `RunListItem`, `RunWithJobVersion`と目的別に型を分離 |
| **D**ependency Inversion | ✅ 適切 | リポジトリはDBインスタンスをコンストラクタ注入、テスト容易性確保 |

### その他の原則

| 原則 | 評価 | 詳細 |
|------|------|------|
| KISS | ✅ 適切 | ポーリングはsetIntervalベースのシンプル実装、過剰な抽象化なし |
| YAGNI | ✅ 適切 | 現時点で必要な機能のみ設計、WebSocketは将来検討として明記 |
| DRY | ✅ 適切 | 既存の`Result<T, E>`パターン、`ApiClient`基底クラスを再利用 |

## 6. 改善提案

### 6.1 必須改善項目（Must Fix）

**なし** - 設計は品質基準を満たしています。

### 6.2 推奨改善項目（Should Fix）

#### 1. ポーリング設定の統合

**現状**: `POLLING_CONFIG`（1秒）と`RUN_POLLING_CONFIG`（5秒）が分散
**提案**: 設定ファイルまたは環境変数で一元管理

```typescript
// src/lib/config/polling.ts
export const POLLING_CONFIGS = {
  jobGeneration: { intervalMs: 1000, maxDurationMs: 900000 },
  runMonitoring: { intervalMs: 5000, maxDurationMs: 1800000 }
} as const;
```

#### 2. エラーログ設計の追加

**現状**: ポーリングエラー時の処理が`error`変数設定のみ
**提案**: サーバーサイドログ、クライアントサイドエラートラッキング設計を追加

```typescript
// ポーリングエラー時の処理追加案
if (!result.ok) {
  error = result.error.message;
  console.error(`[Run ${runId}] Polling error:`, result.error);
  // オプション: エラートラッキングサービスへ送信
}
```

#### 3. ステータスポーリングAPIのレスポンス最適化

**現状**: `{ status, updatedAt }`
**提案**: ETag/Last-Modifiedヘッダー追加で304レスポンス対応

```typescript
// 最適化案
GET /api/runs/:runId/status
Headers: If-None-Match: "etag-value"

Response 304: Not Modified (変更なし)
Response 200: { status, updatedAt, etag }
```

### 6.3 検討事項（Consider）

#### 1. WebSocket/SSE移行パス

現在のポーリング設計を維持しつつ、将来的なWebSocket化のためのインターフェース設計:

```typescript
// 将来の抽象化案
interface RunStatusSubscriber {
  subscribe(runId: string, callback: (status: RunStatus) => void): Unsubscribe;
}

// 現在: PollingSubscriber
// 将来: WebSocketSubscriber
```

#### 2. 一括ステータス取得API

複数Run監視時のポーリング最適化:

```typescript
// 現在: N個のRunに対してN回のAPI呼び出し
// 提案: バッチAPI追加
GET /api/runs/status?ids=run1,run2,run3
```

#### 3. 実行履歴のアーカイブ戦略

長期運用時のデータ増加対策:
- 30日以上前のRunを別テーブルへアーカイブ
- または、SQLite → PostgreSQLマイグレーション検討

## 7. ベストプラクティスとの比較

### 業界標準との差異

| パターン | 採用状況 | 評価 |
|---------|---------|------|
| Repository Pattern | ✅ 採用 | 適切 |
| Result Type Pattern | ✅ 採用 | 適切 |
| Factory Function (Store) | ✅ 採用 | 適切 |
| SSR + Client Hydration | ✅ 採用 | 適切 |
| Polling with Backoff | ⚠️ 部分採用 | エラー時のバックオフ設計はあるが、指数バックオフではない |

### 代替アーキテクチャ案

#### 代替案1: Server-Sent Events (SSE)

- **メリット**: サーバーからのプッシュ通知、接続効率
- **デメリット**: 実装複雑性、既存パターンとの乖離
- **推奨度**: 将来検討

#### 代替案2: GraphQL Subscriptions

- **メリット**: 柔軟なデータ取得、リアルタイム更新
- **デメリット**: 技術スタック変更が大きい、学習コスト
- **推奨度**: 不採用
