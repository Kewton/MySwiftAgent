## 5. リスク評価

| リスク種別 | 内容 | 影響度 | 発生確率 | 対策優先度 |
|-----------|------|--------|---------|-----------|
| **技術的リスク** | Layer 1 検出漏れによる Layer 3 依存 | 中 | 中 | 🟡 中 |
| **技術的リスク** | `[object Object]` 以外の変換パターン | 低 | 低 | 🟢 低 |
| **運用リスク** | 誤検出によるワークフロー生成失敗増加 | 中 | 低 | 🟡 中 |
| **セキュリティリスク** | なし | - | - | - |
| **ビジネスリスク** | 対策不完全による継続的な HTTP 500 | 高 | 低 | 🔴 高 |

### リスク詳細と対策

#### R1: Layer 1 検出漏れによる Layer 3 依存

**シナリオ**: テストデータ生成時に検出できないケース（動的に構築されるオブジェクト等）

**対策**:
- Layer 3（実行時検出）を確実に実装
- 検出漏れ時のフォールバックパスを明確化

#### R2: 誤検出によるワークフロー生成失敗増加

**シナリオ**: 正当なオブジェクト配列使用をエラーとして検出

**対策**:
- stringTemplateAgent を使用するノードのみを検証対象とする
- スキーマに `x-allow-objects: true` のようなオプトアウト機構を検討

## 6. 改善提案

### 必須改善項目（Must Fix）

#### MF-1: Layer間の連携明確化

**問題**: Layer 1 → Layer 3 のフォールバック関係が暗黙的

**修正案**:
```python
# state.py への追加
class ValidationLayerResult(TypedDict):
    layer: Literal["type_validation", "prompt_constraint", "runtime_detection"]
    detected_at: str  # タイムスタンプ
    fallback_triggered: bool  # 前段で検出漏れがあったか
```

#### MF-2: ログレベルの明確化

**問題**: 検出時のログ出力レベルが未定義

**修正案**:
```python
# Layer 1 検出時: logger.warning (再生成で回復可能)
# Layer 3 検出時: logger.error (実行コスト発生後)
```

### 推奨改善項目（Should Fix）

#### SF-1: 検出対象の絞り込み

**問題**: 全配列フィールドを検証すると過検出の可能性

**提案**: stringTemplateAgent の inputs として使用されるフィールドのみを検証対象とする

```python
def _get_string_template_input_fields(yaml_content: str) -> set[str]:
    """YAMLからstringTemplateAgentのinputフィールドを抽出"""
    ...
```

#### SF-2: メトリクス追加

**問題**: 検出頻度や再生成成功率が不明

**提案**: 以下のメトリクスを追加
- `object_array_detection_count` (Counter)
- `test_data_regeneration_success_rate` (Gauge)

### 検討事項（Consider）

#### C-1: stringTemplateAgent の upstream 改修提案

**検討**: @graphai/agents への PR で `JSON.stringify` 自動適用を提案

**評価**: 長期的には根本解決だが、外部依存のため優先度は低

#### C-2: GraphAI専用のオブジェクトシリアライズエージェント

**検討**: `jsonStringifyAgent` のような専用エージェントを graphAiServer に追加

**評価**:
- メリット: ワークフロー内で明示的にシリアライズ可能
- デメリット: ワークフロー複雑化、LLMへの学習コスト

## 7. ベストプラクティスとの比較

### 業界標準との差異

| パターン | 業界標準 | 本設計 | 評価 |
|---------|---------|-------|------|
| **入力検証** | Schema Validation | ✅ Pydantic + カスタム検証 | 適切 |
| **エラーハンドリング** | Fail-Fast / Retry | ✅ 早期検出 + 再生成 | 適切 |
| **多層防御** | Defense in Depth | ✅ 3層検証 | 適切 |
| **可観測性** | Structured Logging | ⚠️ 未定義 | 要改善 |

### 代替アーキテクチャ案

#### 代替案1: stringTemplateAgent ラッパー

```yaml
# graphAiServer に json_string_template_agent を追加
build_prompt:
  agent: jsonStringTemplateAgent  # 自動 JSON.stringify
  inputs:
    data: :source.user_input.complex_object
  params:
    template: "Data: ${data}"
```

| 項目 | 評価 |
|------|------|
| **メリット** | ワークフロー側で明示的にシリアライズ、検証不要 |
| **デメリット** | 新規エージェント実装コスト、LLMへの学習コスト |

#### 代替案2: sample_input 自動正規化

```python
# sample_input_generator.py で自動変換
def _normalize_for_string_template(value: Any) -> Any:
    if isinstance(value, (dict, list)):
        return json.dumps(value, ensure_ascii=False)
    return value
```

| 項目 | 評価 |
|------|------|
| **メリット** | 検出不要、常に安全な値を生成 |
| **デメリット** | テストデータの意図と異なる可能性、予期せぬ副作用 |

## 8. 総合評価

### レビューサマリ

| 項目 | 評価 |
|------|------|
| **全体評価** | ⭐⭐⭐⭐☆（4/5） |
| **設計品質** | 良好 - 既存パターン踏襲、SOLID原則遵守 |
| **実装難易度** | 低 - 明確なコード例、既存との整合性高 |
| **リスク** | 管理可能 - 主要リスクに対策あり |

### 強み

1. **既存パターンとの高い整合性** - Issue #333, #305 のパターンを踏襲
2. **段階的検証アプローチ** - 早期検出 + フォールバックの2段構え
3. **影響範囲の限定** - 外部API変更なし、既存フローへの影響最小
4. **明確な設計判断とトレードオフ** - 各判断の根拠が文書化

### 弱み

1. **Layer間連携の暗黙性** - フォールバック関係が明示的でない
2. **可観測性の不足** - ログレベル、メトリクスが未定義
3. **検出対象の過剰性リスク** - stringTemplateAgent 非使用フィールドも検証

### 総評

本設計は、Issue #340 の問題に対して**実用的かつ保守性の高いソリューション**を提供しています。

既存アーキテクチャパターンを活用した3層防御アプローチは、早期検出と確実な検出のバランスが取れています。stringTemplateAgent の外部ライブラリ制約を考慮した「入力検証強化」の判断も妥当です。

ただし、運用フェーズでの可観測性（ログ、メトリクス）についてはより詳細な設計が必要です。
