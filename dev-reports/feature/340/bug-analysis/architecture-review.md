## 6. 改善提案

### 必須改善項目（Must Fix）

#### MF-1: 無限ループ防止の明示

**問題**: P0-3の条件分岐で `sample_input_generator → test_data_regenerator` ルートが追加されるが、再生成後に再度オブジェクト配列が生成される可能性

**推奨修正**:
- `object_array_regeneration_count` を State に追加
- 再生成上限（例: 2回）を設定
- 上限超過時は `workflow_tester` に進み、エラーログを記録

```python
# state.py に追加
object_array_regeneration_count: int  # 初期値 0

# sample_input_router に追加
def sample_input_router(state: WorkflowGeneratorState) -> Literal[...]:
    has_errors = state.get("has_object_array_errors", False)
    regen_count = state.get("object_array_regeneration_count", 0)
    max_regen = state.get("max_object_array_regeneration", 2)

    if has_errors and regen_count < max_regen:
        return "test_data_regenerator"
    elif has_errors:
        logger.warning(f"Max object array regeneration exceeded ({max_regen})")
    return "workflow_tester"
```

#### MF-2: P0-2 型検証の網羅性不足

**問題**: 設計方針書の `_enum_or_default` 修正案は `string`, `number`, `integer` のみ対応

**推奨修正**: `boolean` 配列と混合型配列の検証を追加

```python
elif items_type == "boolean":
    if all(isinstance(item, bool) for item in default):
        return default
    return None
```

#### MF-3: P1-6, P1-7 の詳細設計不足

**問題**: P1-6 (LLM Evaluation) と P1-7 (self_repair) の具体的なコード変更が記載されていない

**推奨修正**: 設計方針書に具体的なプロンプト追加内容とコード変更箇所を追記

---

### 推奨改善項目（Should Fix）

#### SF-1: テスト設計の不足

**問題**: 統合テストが `test_object_array_routing.py` のみ

**推奨修正**: 以下のテストケースを追加
- 複数回再生成後の正常フロー
- 再生成上限超過時のフロー
- 既存ワークフローへの回帰テスト

#### SF-2: メトリクス/ログの強化

**問題**: 5層防御の各層での検出状況を把握するメトリクスがない

**推奨修正**:
- 各層での検出回数をログに記録
- Langfuseトレースに検出結果を追加

#### SF-3: P0-1 プロンプトの効果測定方法

**問題**: プロンプト追加の効果を測定する方法が不明確

**推奨修正**:
- プロンプト追加前後でのdefault値品質比較
- A/Bテストまたは回帰テストでの検証

---

### 検討事項（Consider）

#### C-1: Layer 0 と Layer 1 の統合可能性

**検討理由**: Layer 0（スキーマ生成時）と Layer 1（sample_input生成時）は同種の検証

**代替案**: interface_definition.py での検証のみに集約し、sample_input_generator での検証をスキップ

**結論**: **現状維持推奨** - 多層防御の原則に従い、両層で検証を維持

#### C-2: GraphAI側での対応可能性

**検討理由**: stringTemplateAgentにオブジェクト→JSON文字列変換機能を追加

**代替案**: GraphAI/graphai-agents にPR提出

**結論**: **長期検討** - 上流での修正が根本解決だが、時間がかかるため多層防御で対応

## 7. ベストプラクティスとの比較

### 業界標準との差異

| 項目 | 業界標準 | 本設計 | 評価 |
|------|---------|-------|------|
| **入力検証** | 早期検証（Fail Fast） | 多層防御 | ✅ より堅牢 |
| **エラーハンドリング** | 例外ベース | State フラグベース | ⚠️ LangGraph制約内で妥当 |
| **スキーマ検証** | JSON Schema validator | 手動検証 + LLMプロンプト | ⚠️ LLM生成のため妥当 |

### 代替アーキテクチャ案

#### 代替案1: 即時エラー返却

**説明**: Layer 1でオブジェクト配列を検出した場合、即座にエラーを返却

**メリット**:
- シンプル
- 処理時間短縮

**デメリット**:
- リトライの機会を失う
- ユーザー体験悪化

**採用判断**: **不採用** - 成功率向上を優先

#### 代替案2: 3層防御（P0のみ）

**説明**: P0-1, P0-2, P0-3のみ実装し、P1, P2はスキップ

**メリット**:
- 実装コスト削減
- 複雑性低減

**デメリット**:
- LLM出力の不確実性に対応できない
- 再生成時の品質担保なし

**採用判断**: **条件付き採用可能** - P0で効果検証後、P1/P2の必要性を再評価
