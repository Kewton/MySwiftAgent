| 概念 | 定義A | 定義B | 整合性 | 対処案 |
|-----|------|------|--------|--------|
| 回復戦略 | | | | |
| エラータイプ | | | | |
| ステータス | | | | |

**チェック方法**:
```bash
# 同一概念の複数定義を検索
grep -rn "class.*Enum\|= Enum" --include="*.py"
grep -rn "ALLOWED_.*=\|_PATTERN.*=" --include="*.py"
```

#### 4.5.2 成功条件整合性チェック（Issue #360追加）

**重要**: 上流処理の成功条件と下流処理の期待値が一致しているか確認。

| 上流処理 | 上流の成功条件 | 下流処理 | 下流の期待値 | 整合性 |
|---------|--------------|---------|------------|--------|
| | 1件でも成功すればOK | | 全件成功を要求 | ❌ 矛盾 |
| | 部分成功を許容 | | 全件完了を検証 | ❌ 矛盾 |

**典型的な矛盾パターン**:
- 登録処理: `success = len(updated) > 0`（1件でもOK）
- 検証処理: 全件が更新されていないとエラー
- 結果: 部分成功時に後続処理で失敗

**チェック方法**:
```bash
# 成功条件の定義を検索
grep -rn "success.*=.*len\|overall_success" --include="*.py"
grep -rn "partial.*success\|all_succeeded" --include="*.py"

# 検証処理を検索
grep -rn "validate.*pending\|can_proceed\|is_complete" --include="*.py"
```

#### 4.5.3 エラー伝播整合性チェック（Issue #360追加）

**重要**: 「非致命的」として処理されるエラーが、後続の「必須検証」と矛盾していないか確認。

| エラー発生箇所 | 処理方法 | 後続検証 | 矛盾 |
|--------------|---------|---------|------|
| | 例外をwarningでログして続行 | 同じ処理の完了を必須検証 | ❌ |
| | 失敗をnon-fatalとして無視 | 失敗した項目を後で検出 | ❌ |

**典型的な矛盾パターン**:
```python
# 上流: 例外を非致命的として処理
except Exception as e:
    logger.warning("non-fatal: %s", e)
    # Continue...

# 下流: 上流処理の完了を検証
if not all_completed:
    raise Error("incomplete")  # 上流で無視したエラーがここで顕在化
```

**チェック方法**:
```bash
# 非致命的エラー処理を検索
grep -rn "non-fatal\|# Continue\|logger.warning" --include="*.py"

# 後続の必須検証を検索
grep -rn "can_proceed\|is_valid\|validate" --include="*.py"
```

#### 4.5.4 部分成功の伝播チェック（Issue #360追加）

部分成功（partial success）の情報が適切に伝播されているか確認：

| 処理 | 部分成功の発生 | 戻り値での通知 | 呼び出し元での処理 | 問題 |
|-----|--------------|---------------|------------------|------|
| | failed_items を検出 | 戻り値に含める | 無視して続行 | ❌ 情報ロス |
| | 一部タスク失敗 | success=True | 全成功として扱う | ❌ 誤認 |

**チェック方法**:
```bash
# 部分成功の戻り値を検索
grep -rn "failed_.*=\|partial" --include="*.py" -A2

# 戻り値の使用箇所を検索
grep -rn "result\[.success.\]\|\.success" --include="*.py"
```

#### 4.5.5 検証タイミング整合性チェック（Issue #360追加）

検証が適切なタイミングで行われているか確認：

| 検証内容 | 現在のタイミング | 適切なタイミング | 問題 |
|---------|----------------|-----------------|------|
| | 処理完了後 | 処理開始前 | 無駄な処理発生 |
| | 最終段階で一括 | 各段階で即座に | エラー検出遅延 |

**チェック方法**:
```bash
# 検証処理の呼び出し位置を確認
grep -rn "def validate\|async def validate" --include="*.py"
```

#### 4.5.7 LLMプロンプトルール整合性チェック

LLMプロンプト内のルールが矛盾していないか確認：

| ルール種別 | セクションA | セクションB | 矛盾 | 対処案 |
|-----------|------------|------------|------|--------|
| セキュリティルール | | | | |
| APIルール | | | | |
| フォーマットルール | | | | |

**典型的な矛盾パターン**:
- セキュリティルールで「HTTPS必須」、APIルールで「http://localhost」を使用
- バリデーションルールで禁止、サンプルコードで使用

**チェック方法**:
```bash
# プロンプトルール内の矛盾を検出
grep -n "HTTPS\|HTTP" path/to/rules.py
grep -n "localhost\|127.0.0.1" path/to/rules.py
```

#### 4.5.8 テスト対象/検証手法整合性チェック

テストが適切な検証手法を使用しているか確認：

| テスト対象 | 期待手法 | 実際の手法 | 問題 |
|-----------|---------|-----------|------|
| JSON出力 | JSONバリデーション | YAMLバリデーション | 不一致 |
| API呼び出し | 実APIテスト | モック | E2E不足 |

**チェック方法**:
```bash
# テストファイルの検証手法を確認
grep -n "validate_yaml\|validate_json" tests/
grep -n "Mock\|patch" tests/
```
