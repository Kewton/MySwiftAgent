# 要件定義スキル

ユーザーストーリー、受入条件、技術要件を生成します。

## 適用条件

以下のキーワード・文脈で自動的に適用：
- 要件定義、要件整理
- ユーザーストーリー作成
- 受入条件、Acceptance Criteria
- 機能要件、非機能要件
- 技術的制約の整理

## 実行内容

経験豊富な要件定義スペシャリストとして、以下の手順で要件定義を作成：

### 0. 現状調査（必須）

#### Issue情報の取得
```bash
gh issue view [Issue番号] --json title,body,labels,assignees
```

#### 関連ドキュメントの確認
対象プロジェクトに応じて必須ドキュメントを読み込み：
- expertAgent: `expertAgent/docs/API_REFERENCE.md`
- graphAiServer: `graphAiServer/docs/GRAPHAI_WORKFLOW_GENERATION_RULES.md`
- myAgentDesk: `myAgentDesk/README.md`
- 全サービス: `docs/arch/service-dependencies.md`

#### 既存実装の調査
Task tool (subagent_type=Explore) を使用：
- 関連する既存機能・モジュール
- 類似機能の実装例
- 使用されている設計パターン

### 1. ユーザーストーリーの作成

```
As a [ユーザー種別]
I want to [達成したいこと]
So that [期待される価値/ビジネス価値]
```

### 2. 受入条件（Acceptance Criteria）

既存の類似機能の受入条件を参考に、一貫性のある基準を設定：

- **Given**: 前提条件
- **When**: アクション
- **Then**: 期待される結果

### 3. 機能要件

既存実装との整合性を考慮した要件定義：

- **必須機能（Must Have）**: 必ず実装
- **あると良い機能（Nice to Have）**: 可能なら実装
- **将来的な拡張（Future Enhancement）**: 次期対応

### 4. 非機能要件

プロジェクトの既存基準に合わせた非機能要件：

- パフォーマンス要件
- セキュリティ要件
- ユーザビリティ要件
- 互換性要件

### 5. 技術的制約

現状調査で把握した制約を反映：

- 使用する技術スタック（既存スタックとの整合性）
- 既存システムとの連携
- データ形式・API仕様（既存APIとの一貫性）

### 6. リスクと対策

調査結果に基づくリスク評価：

- 技術的リスク
- ビジネスリスク
- 対策案

## 出力形式

出力先: `dev-reports/feature/issue/{issue_number}/requirements.md`

```markdown
# 要件定義書: [機能名]

## 現状調査サマリ
[調査結果のサマリ]

## ユーザーストーリー
[ストーリー]

## 受入条件
[条件リスト]

## 機能要件
[要件リスト]

## 非機能要件
[要件リスト]

## 技術的制約
[制約リスト]

## リスクと対策
[リスク評価]

## 参照ドキュメント
[読み込んだドキュメントのリスト]
```

GitHub Issueの説明欄に直接貼り付け可能な形式で出力。

## 注意事項

1. **現状調査は必須**: 調査をスキップして要件定義を作成しないこと
2. **既存パターンの尊重**: 調査で判明した設計パターン・命名規則に従うこと
3. **重複回避**: 既存機能との重複がある場合は、拡張または統合を検討
4. **ドキュメント参照の明記**: 参照したドキュメントを要件定義書に記載すること

## 明示的呼び出し

スラッシュコマンドでも呼び出し可能：
```
/requirements [Issue番号または機能概要]
```
