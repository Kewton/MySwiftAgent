# 要件定義スキル

## 概要
ユーザーストーリー、受入条件、技術要件を生成するスキルです。

## 使用方法
- `/requirements [Issue番号または機能概要]`
- 「[機能名]の要件定義を作成してください」
- 「Issue #123の要件定義を作成してください」

## 実行内容

あなたは経験豊富な要件定義スペシャリストです。以下の手順で要件定義を作成してください：

---

### 0. 現状調査（必須）

**重要**: 要件定義を作成する前に、必ず以下の現状調査を実施してください。

#### 0.1 Issue情報の取得（Issue番号指定時）

Issue番号が指定された場合、以下を実行：

```bash
gh issue view [Issue番号] --json title,body,labels,assignees
```

取得した情報から：
- 対象プロジェクト（ラベルから判定: `project: expertAgent`, `project: myAgentDesk`等）
- 関連Issue/PRのリンク
- 既存の議論内容

#### 0.2 関連ドキュメントの確認

CLAUDE.mdの「必須参照ドキュメント」を確認し、対象プロジェクトに応じて以下を読み込み：

| プロジェクト | 必須ドキュメント |
|-------------|----------------|
| expertAgent | `expertAgent/docs/API_REFERENCE.md`, `docs/spec/job-generation-workflow.md` |
| graphAiServer | `graphAiServer/docs/GRAPHAI_WORKFLOW_GENERATION_RULES.md` |
| myAgentDesk | `myAgentDesk/README.md` |
| 全サービス | `docs/arch/service-dependencies.md` |

#### 0.3 既存実装の調査（Task tool使用）

Task tool (subagent_type=Explore) を使用して以下を調査：

```
調査項目：
1. 「関連する既存機能・モジュールは何か」
2. 「類似機能の実装例はあるか」
3. 「使用されている設計パターンは何か」
```

**調査の目的**:
- 既存コードベースとの整合性確保
- 重複実装の防止
- 命名規則・ディレクトリ構造のルール把握

#### 0.4 調査結果のサマリ

現状調査の結果を以下の形式でまとめる：

```markdown
## 現状調査サマリ

### 対象プロジェクト
- プロジェクト名: [特定されたプロジェクト]
- 関連モジュール: [調査で見つかった関連モジュール]

### 既存の類似機能
- [類似機能1]: [概要と場所]
- [類似機能2]: [概要と場所]

### 使用されている設計パターン
- [パターン1]: [使用箇所と目的]

### 参照したドキュメント
- [ドキュメント1]: [関連する内容のサマリ]

### 制約事項
- [調査で判明した制約1]
- [調査で判明した制約2]
```

---

### 1. ユーザーストーリーの作成

現状調査の結果を踏まえて、ユーザーストーリーを作成：

```
As a [ユーザー種別]
I want to [達成したいこと]
So that [期待される価値/ビジネス価値]
```

### 2. 受入条件（Acceptance Criteria）

既存の類似機能の受入条件を参考に、一貫性のある基準を設定：

- Given: 前提条件
- When: アクション
- Then: 期待される結果

### 3. 機能要件

既存実装との整合性を考慮した要件定義：

- 必須機能（Must Have）
- あると良い機能（Nice to Have）
- 将来的な拡張（Future Enhancement）

### 4. 非機能要件

プロジェクトの既存基準に合わせた非機能要件：

- パフォーマンス要件
- セキュリティ要件
- ユーザビリティ要件
- 互換性要件

### 5. 技術的制約

現状調査で把握した制約を反映：

- 使用する技術スタック（既存スタックとの整合性）
- 既存システムとの連携
- データ形式・API仕様（既存APIとの一貫性）

### 6. リスクと対策

調査結果に基づくリスク評価：

- 技術的リスク
- ビジネスリスク
- 対策案

---

## 出力フォーマット

Markdownフォーマットで構造化された要件定義書を生成します。

### 出力構成

```markdown
# 要件定義書: [機能名]

## 現状調査サマリ
[調査結果のサマリ]

## ユーザーストーリー
[ストーリー]

## 受入条件
[条件リスト]

## 機能要件
[要件リスト]

## 非機能要件
[要件リスト]

## 技術的制約
[制約リスト]

## リスクと対策
[リスク評価]

## 参照ドキュメント
[読み込んだドキュメントのリスト]
```

GitHub Issueの説明欄に直接貼り付け可能な形式で出力してください。

---

## 注意事項

1. **現状調査は必須**: 調査をスキップして要件定義を作成しないこと
2. **既存パターンの尊重**: 調査で判明した設計パターン・命名規則に従うこと
3. **重複回避**: 既存機能との重複がある場合は、拡張または統合を検討
4. **ドキュメント参照の明記**: 参照したドキュメントを要件定義書に記載すること
