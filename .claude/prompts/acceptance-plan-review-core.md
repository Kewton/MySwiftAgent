# 受入テスト計画レビュー コアプロンプト

このプロンプトは、受入テスト計画のレビューを行うサブエージェントから実行されます。

---

## 目的

受入テスト計画（acceptance-plan.md）をレビューし、以下を確認します：

1. **Issue網羅性**: Issue記載の受入条件がすべてカバーされているか
2. **設計方針網羅性**: design-policy.md の内容が検証項目に含まれているか
3. **テスト環境・方法の妥当性**: 実行可能で意味のあるテストになっているか
4. **テスト項目の妥当性**: E2E視点で実際の動作を検証できているか

---

## 入力情報

### 必須参照ドキュメント

1. **受入テスト計画書**:
   ```bash
   cat dev-reports/feature/issue/{issue_number}/acceptance-plan.md
   ```

2. **Issue情報**:
   ```bash
   gh issue view {issue_number} --json number,title,body,labels
   ```

3. **設計方針書**:
   ```bash
   cat dev-reports/feature/issue/{issue_number}/design-policy.md
   ```

4. **作業計画書**（存在する場合）:
   ```bash
   cat dev-reports/feature/issue/{issue_number}/work-plan.md
   ```

---

## レビュー観点

### 1. Issue網羅性レビュー

Issue本文から受入条件を抽出し、計画書のテスト項目と照合します。

**チェック項目**:

| チェック | 内容 | 判定 |
|---------|------|------|
| AC-1 カバー | 受入条件1がテスト項目に含まれるか | ✅/❌ |
| AC-2 カバー | 受入条件2がテスト項目に含まれるか | ✅/❌ |
| ... | ... | ... |

**抽出方法**:

```bash
# Issue本文から受入条件セクションを抽出
gh issue view {issue_number} --json body --jq '.body' | grep -A 100 "## 受入条件"
```

**レビュー結果フォーマット**:

```markdown
## Issue網羅性レビュー

### 抽出された受入条件
1. [AC-1]: {受入条件1}
2. [AC-2]: {受入条件2}

### カバレッジ確認
| 受入条件 | 対応テスト項目 | 判定 |
|---------|--------------|------|
| AC-1 | TC-001, TC-002 | ✅ カバー |
| AC-2 | TC-003 | ✅ カバー |
| AC-3 | なし | ❌ 未カバー |

### 未カバー項目
- AC-3: {未カバーの受入条件}
  - **改善提案**: TC-XXX を追加し、以下を検証
    - {検証内容}
```

### 2. 設計方針網羅性レビュー

design-policy.md の主要な設計判断がテスト項目で検証されているか確認します。

**確認すべき設計方針セクション**:

| セクション | 確認内容 |
|-----------|---------|
| アーキテクチャ設計 | レイヤー構成、コンポーネント配置 |
| 技術選定 | 選定技術が使用されているか |
| 設計パターン | 指定パターンが適用されているか |
| API設計 | エンドポイント、リクエスト/レスポンス形式 |
| セキュリティ設計 | セキュリティ要件の実装 |
| テスト計画 | 設計方針書のテスト計画との整合性 |

**レビュー結果フォーマット**:

```markdown
## 設計方針網羅性レビュー

### 設計方針の主要項目
1. [DP-1]: {設計方針1}
2. [DP-2]: {設計方針2}

### カバレッジ確認
| 設計方針 | 対応テスト項目 | 判定 |
|---------|--------------|------|
| DP-1: Strategy Pattern | DP-1検証テスト | ✅ カバー |
| DP-2: API設計 | TC-001 | ✅ カバー |
| DP-3: セキュリティ | なし | ❌ 未カバー |

### 未カバー項目
- DP-3: {未カバーの設計方針}
  - **改善提案**: セキュリティテスト TC-XXX を追加
    - HTTPS強制の検証
    - 認証トークンの検証
```

### 3. テスト環境・方法の妥当性レビュー

**チェック項目**:

| チェック | 内容 | 判定基準 |
|---------|------|---------|
| サービス一覧 | 必要なサービスがすべて記載されているか | プロジェクトに応じた必須サービス |
| ヘルスチェック | 各サービスのヘルスチェック方法が記載されているか | URL + コマンド |
| 起動コマンド | 環境起動コマンドが正しいか | 実行可能なコマンド |
| 環境変数 | 必要な環境変数がすべて記載されているか | APIキー等 |
| テストデータ | テストデータの準備方法が記載されているか | 存在する場合 |

**プロジェクト別必須サービス**:

| プロジェクト | 必須サービス |
|-------------|-------------|
| expertAgent | expertAgent, myVault |
| graphAiServer | graphAiServer, myVault, expertAgent |
| myAgentDesk | myAgentDesk, expertAgent, myVault |
| jobqueue | jobqueue, myVault |

### 4. テスト項目の妥当性レビュー

各テスト項目が実際にE2E視点で動作を検証できているか確認します。

**チェック項目**:

| チェック | 内容 | 判定基準 |
|---------|------|---------|
| E2E視点 | 実際のAPI呼び出しで検証しているか | curl/requestsを使用 |
| モック使用 | 不要なモックを使用していないか | 外部APIのみ許可 |
| 期待結果 | 具体的な期待結果が記載されているか | HTTPステータス + レスポンス |
| 再現性 | 他者が実行できるか | 具体的なコマンド/手順 |
| デッドコード検証 | 実装機能の使用確認があるか | 呼び出し確認 |

**禁止パターンの検出**:

```markdown
### 禁止パターン検出

| パターン | 検出結果 | 対象テスト項目 |
|---------|---------|--------------|
| 全面モック | ❌ 検出 | TC-003 |
| ファイル存在確認のみ | ✅ なし | - |
| ヘルスチェックのみ | ✅ なし | - |
```

### 5. サービス間データフロー検証（Issue #385追加）

**重要**: テストデータが「空」「null」を正常ケースとして扱っていないか確認。

#### 5.1 空配列/null使用の検出

```markdown
### 空配列/null検出

| 検出パターン | テストファイル/項目 | 問題 | 判定 |
|------------|------------------|------|------|
| capabilities=[] | TC-001 | 本番では空でない | ❌ 禁止 |
| capabilities: [] | TC-002 | 本番では空でない | ❌ 禁止 |
| trace_id=None | TC-003 | 要確認 | ⚠️ 確認 |
```

**チェック方法**:
- テスト項目のテストデータを確認
- 「空配列」「null」「None」が正常ケースとして使用されていないか
- 本番で値が必須のフィールドがテストでも値を持っているか

#### 5.2 データフロー完全性検証

```markdown
### データフロー検証項目

| 送信元 | データ項目 | 送信先 | テスト有無 | 判定 |
|--------|-----------|--------|----------|------|
| expertAgent | capabilities | mySwiftAgentCore | TC-XXX | ✅/❌ |
| expertAgent | trace_id | mySwiftAgentCore | TC-XXX | ✅/❌ |
```

**却下条件**:
- サービス間で渡される必須データ項目のテストが存在しない
- テストデータとして空配列/nullを正常ケースとして使用している

**レビュー結果フォーマット**:

```markdown
## サービス間データフロー検証レビュー

### 空配列/null検出結果
| 検出パターン | テスト項目 | 問題 | 判定 |
|------------|----------|------|------|
| capabilities=[] | TC-001 | 本番では実データ必須 | ❌ 要修正 |

### データフロー検証結果
| データ項目 | テスト有無 | 判定 |
|-----------|----------|------|
| capabilities | ❌ なし | 要追加 |
| trace_id | ✅ TC-002 | OK |

### 結果
- 判定: ❌ FAIL（空配列/nullテストを検出）
- 改善必須: テストデータを実データに置き換え
```

**レビュー結果フォーマット**:


## 総合判定

### 判定基準

| 判定 | 条件 |
|------|------|
| ✅ **承認** | 全レビュー項目がパス、または軽微な改善のみ |
| ⚠️ **条件付き承認** | 一部改善が必要だが、実行可能 |
| ❌ **却下** | 重大な問題があり、計画の見直しが必要 |

### 重大な問題（却下条件）

- 受入条件の50%以上が未カバー
- 設計方針の主要項目が未カバー
- テスト環境が実行不可能
- 全テスト項目がモックのみ
